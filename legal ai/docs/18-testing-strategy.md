> **Purpose:** Complete implementation blueprint for `Testing Strategy`.
>
> This document is the authoritative specification for building this service. Developers must be able to understand **what the service does, what it owns, what it receives, what it produces, how it connects to the rest of the platform, and what rules it must follow** without requiring additional architectural decisions.

# 1. SERVICE IDENTITY

## 1.1 Service Name

`Legal AI Platform - Testing Strategy`

## 1.2 Service ID

`sys-testing-core-platform`

## 1.3 Service Category

`Platform Engineering & Quality Assurance`

## 1.4 Service Type

`Development Standard`

## 1.5 Primary Responsibility

Clearly define the **single primary responsibility** of this service.

The Testing Strategy must:

* Define exactly how the backend is tested to ensure business logic is correct, AI outputs are reliable, and security boundaries are enforced.
* Establish `pytest` as the standard framework.
* Dictate how to properly mock expensive external resources (like OpenAI APIs and AWS S3) during unit tests.

The service must **not** test frontend UI components (that is the domain of React/Cypress).

## 1.6 Business Purpose

Explain why this service exists and what problem it solves.
Legal software has a zero-tolerance policy for data leaks or inaccurate logic. If a bug allows User A to see User B's contract, the business fails. A rigorous, automated testing strategy ensures that as the platform grows rapidly, new features do not break existing security or functional guarantees.

## 1.7 User Value

Explain what the user gains from this service.
A stable, reliable product. Updates and new features roll out smoothly without introducing regressions or downtime.

## 1.8 Final Outcome

Define exactly what successful completion of this service produces.
A standardized `tests/` directory structure, clear `pytest` fixtures for database state, and strict rules for CI/CD pipeline execution.

# 7. BUSINESS RULES

This section contains the **non-negotiable rules** of the service.

## 7.1 Core Rules

* **Isolation:** Tests must NEVER run against the production database. A dedicated, ephemeral `test_db` must be spun up and torn down for integration tests.
* **No Live AI Calls:** Unit tests must NEVER make real HTTP calls to OpenAI or Anthropic (it costs money and is slow). Use `respx` or mock the `AIProviderLayer`.

# 9. AI RESPONSIBILITY

*(This section addresses how to test AI)*

## 9.1 AI Purpose

* Testing generative AI is notoriously difficult because outputs are non-deterministic (different every time).

## 9.4 AI Rules

* **Evaluation Testing:** Instead of strict unit tests, AI capabilities (like the RAG pipeline) should use "Evaluation Sets" (e.g., using `Ragas` or `TruLens`).
* Create a golden dataset of 50 legal questions and their known correct answers. Run the AI pipeline against this dataset during weekly integration builds to ensure accuracy hasn't regressed.

# 12. BACKGROUND PROCESSING

## 12.1 Background Tasks

* Test Celery tasks synchronously by setting `app.conf.task_always_eager = True` in the pytest fixture. This executes the task immediately instead of sending it to Redis.

# 13. DATABASE RESPONSIBILITY

## 13.1 Owned Data
* Ephemeral Test Database.

## 13.5 Database Rules

* **Clean Slate:** Every individual test MUST start with a clean database. Use pytest fixtures to create database transactions that rollback immediately after the test yields, ensuring zero cross-test state contamination.

# 14. STORAGE REQUIREMENTS

# 31. ACCEPTANCE CRITERIA

### Functional
* [ ] Developers can run `pytest` locally and get instant feedback.
* [ ] Database state does not leak between tests.
* [ ] External APIs (OpenAI, AWS) are successfully mocked.
* [ ] CI pipeline blocks merges if tests fail.

---

# 32. DEFINITION OF DONE

The Testing Strategy is **DONE** when the `tests/` directory is fully structured, a `conftest.py` successfully provisions an ephemeral Postgres database, and developers can confidently test their code without needing live API keys.

---

# 33. IMPLEMENTATION RULES

1. **Keep business logic inside the service responsible for it.**
2. **Database ownership must be explicit (Rollback after tests).**
3. **Documents must remain associated with the correct workspace and permissions (Test this relentlessly).**
4. **Secrets must never be committed to source control (Do not use real keys in tests).**
