# Legal AI Platform (Document Understanding)

> **Purpose:** Complete implementation blueprint for `Document Understanding`.
>
> This document is the authoritative specification for building this service. Developers must be able to understand **what the service does, what it owns, what it receives, what it produces, how it connects to the rest of the platform, and what rules it must follow** without requiring additional architectural decisions.

---

# 1. SERVICE IDENTITY

## 1.1 Service Name

`Legal AI Platform - Document Understanding`

## 1.2 Service ID

`sys-common-document-understanding`

## 1.3 Service Category

`Common Infrastructure / Data Preparation`

## 1.4 Service Type

`Background Worker Pipeline`

## 1.5 Primary Responsibility

Clearly define the **single primary responsibility** of this service.

The Document Understanding service must:

* Consume the raw, linear text blocks generated by the `OCR & Text Extraction` service.
* Perform **Semantic Chunking**: Grouping text into logical legal blocks (e.g., keeping an entire clause together rather than splitting it arbitrarily at 500 characters).
* Generate Vector Embeddings for every chunk and store them in the Vector Database (Qdrant).
* Perform a baseline metadata extraction: Document Title, Document Type (Lease, NDA, MSA), Governing Law, Effective Date, and the Parties involved.

The service must **not** perform deep risk analysis or compliance checking (Handled by specialized domain services). It only prepares the document so that those specialized services can work efficiently.

## 1.6 Business Purpose

Explain why this service exists and what problem it solves.
If you feed an entire 100-page contract into an LLM, it will hit token limits and hallucinate. If you chop a contract into blind 500-word pieces, the AI might lose the context that a specific paragraph belongs to the "Indemnification" section. This service structures the document semantically and vectorizes it, creating the foundational "index" that allows the Chat and Search services to instantly find relevant clauses later.

## 1.7 User Value

Explain what the user gains from this service.
When a user opens a newly uploaded document, they instantly see a generated summary of its basic facts (Who, What, When) on the sidebar, and they can immediately start chatting with it because it has been fully indexed.

## 1.8 Final Outcome

Define exactly what successful completion of this service produces.
A fully vectorized document stored in Qdrant, and updated base metadata fields in the PostgreSQL `documents` table.

# 4. SERVICE WORKFLOW

Define the complete internal workflow.

### Document Understanding Pipeline

```text
CELERY WORKER receives `TextExtractionCompleteEvent(doc_id)`
  ↓
Fetch all `document_chunks` for `doc_id` ordered by sequence.
  ↓
[Phase 1: Semantic Chunking & Embedding]
Group chunks by Markdown headers (`#`, `##`) or logical breaks to form "Semantic Blocks" (target ~300-500 tokens per block).
For each Semantic Block:
  Call AIGateway `/embeddings` endpoint.
  Store resulting vector in Qdrant attached to the `chunk_id`.
  ↓
[Phase 2: Baseline Metadata]
Take the first 5 chunks (usually contains Title, Parties, Date).
Send to AIGateway LLM: "Extract Title, Doc Type, Parties, Date, Governing Law".
Parse JSON response.
  ↓
Update `documents` table with extracted metadata.
Mark `documents.status` = `READY`.
Publish `DocumentReadyEvent`.
```

# 7. BUSINESS RULES

This section contains the **non-negotiable rules** of the service.

## 7.1 Core Rules

* **Multi-Tenant Vector Security:** Qdrant collections must be partitioned or strictly filtered by `workspace_id`. A search by Workspace A must *never* return vector matches from Workspace B's documents.
* **Semantic Chunking over Fixed Chunking:** The chunker must attempt to break text at paragraph or section boundaries. A chunk should not split a sentence in half just because it hit a 500-token limit.

## 7.2 Validation Rules
N/A

## 7.3 Decision Rules
* If the LLM cannot confidently determine the Governing Law from the first few pages, it should leave it `null` rather than guessing.

## 7.4 Failure Rules
* If the Embedding API rate-limits the worker, the task must retry using Celery's exponential backoff.

## 7.5 Boundary Rules
N/A

# 9. AI RESPONSIBILITY

## 9.1 AI Purpose
1. Vector Embedding Generation (Dense representation of text meaning).

## 9.4 AI Rules
* **Embedding Model:** Use a high-quality embedding model optimized for retrieval (e.g., `text-embedding-3-large` or `voyage-law-2`). Legal text requires models trained on legal vocabulary to distinguish subtle differences between clauses.

# 10. AI PROMPT RESPONSIBILITY

## 10.1 System Prompt (Metadata Extraction)
```text
You are an expert paralegal. Analyze the beginning of this document and extract its core metadata.
If a piece of information is not explicitly stated in the text provided, return null.
Do not guess. Output strictly as JSON.
```

## 10.4 Prompt Rules
* The prompt only receives the first ~2000 tokens of the document, as the title, parties, and effective dates are almost universally located on the first two pages of a contract.

# 35. FINAL SERVICE SUMMARY

## What it does
Prepares raw text for advanced AI analysis by generating vector embeddings and extracting basic file metadata.

## What the user sees
The document transitions from "Processing" to "Ready", and its metadata (Title, Date, Parties) magically populates in the file explorer.

## What happens in the background
The service intelligently chunks the raw text, converts those chunks into high-dimensional vectors for semantic search, stores them securely in a multi-tenant vector database, and uses a fast LLM to read the first page and extract the core facts of the contract.

## What it receives
Raw text chunks.

## What it produces
Vector embeddings in Qdrant and structured metadata in PostgreSQL.

## Success means
The foundational "brain" of the document is built perfectly, allowing all subsequent Chat and Risk tools to instantly find exactly what they are looking for without hitting token limits.
